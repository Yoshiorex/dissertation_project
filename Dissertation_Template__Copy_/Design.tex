\section{Problem Formulation}
\label{sec:ProblemFormulation}

This section should provide the reader with an overall description of the problem that will be addressed in the dissertation. In contrast to a generic discussion of the dissertation topic in the Introduction chapter, this section should provide a detailed discussion of the problem that has been identified based on the existing work that has been discussed in the preceeding chapter. 

In some dissertations, it may make sense to convert this section into a short chapter of its own which follows the discussion of the existing work and preceeds the discussion of the work of the dissertation.



The problem to be addressed by this dissertation is the difficulty of extending and maintaining the codebase of the testbuilder program due to the fact that it is written in python. the testbuilder program is the program that takes a formal model of a RTEMS system and turns it into C test code. python excelled during the creation of the testbuilder program due to its easy use for quick protoyping and smooth iterations. the testbuilder was able to be rapidly developed within the time constraints of an academic year. 

Unfortunately now that the system is written entirely in python, it means that certain parts of the system are difficult to extend. specifically spin2test.py and the module it relies on, refinecommand.py. Due to the imperative style that the program was written in, the refine_command program has numerous elements that make it difficult to alter.

1. mutable state
the python in refine_command makes extensive use of state and mutable state attributes for tracking things like whether a spin line is written in the context of being in a struct or as a standalone line. this makes the flow of data and tracking the state through a function difficult to follow and harder to reason about. altering an existing variable means contending with the delicate state setup. 

2.non exhaustive pattern matching
in the main part of the code, where spin lines turn into test code, extensive use of the match keyword is used. this is used to match the spin line to the correct test code. this system works but python doesn't enforce completeness and the catch all "case:_" at the end matches for any cases not accounted for in the code. this is not ideal coding, it hides potential bugs and makes it easy to forget to handle a new annotation type. 

3.mix of concerns
the python includes a monolithic main method of 150 lines which suffers from a mix of concerns. it handles Keyword-specific logic, State updates (e.g., toggling inSTRUCT), Lookups in ref_dict, Code accumulation (via addCode, defCode, declCode). this makes it more difficult to alter the code and test specific pieces of logic.

Haskell will be leveraged to solve the problems listed above in an elegant way.
1. Mutable states
haskell requires purity in its functions. every input maps to exactly one output. this allows for clear local reasoning and makes the program flow transparent.

2. non exhasutive pattern matching
haskells compiler requires completeness so having a non comprehensive match function isnt even possible. you are required to cover all cases and when adding new annotation types you have a built in reminder to build in test cases.

3. mix of concerns
haskell specialises in decomposing functions into smaller more atomic functions. side effects are not allowed and functions are allowed to be passed and retunred to higher order functions, increasing the readability and reusability of the code.


a functional language, like Haskell, is the clear choice for refactoring this program because it's using a python superset called coconut. this superset compiles to python and all valid python syntax is valid coconut. what it does is add functional programming constructs like pattern matching to python. eventually python would add pattern matching in python 3.10 but the functional aspects remained and so when reworking the code, it makes sense use a language like Haskell so full advantage can be taken of functional programming, such as lazy evaluation and functional purity, aspects not in coconut

\section{Overview of the Design}
\label{sec:OverviewOfDesign}
A description of the approach that addresses the problem identified above.

Due to the fact that the files to be changed exist within a larger codebase, of which the workings are complex and multifaceted, a careful approach will be taken to the conversion of the files. To avoid the issues found with multilingual developement, such as difficulty with data flows and intepreting errors, i will be implementing a bridge program. this bridge will have the purpose of selecting between the original python code and the new haskell code as the code is converted. in the beginning the bridge will choose only the original python but then on a function by function bsais, will startusing the haskell. this approach allows the continous comparision of the programs output with the ouput of the pure python in order to ensure parity.
The system allows for constant end to end testing, which is the important for a system with exisitng functionality, as unit testing specific functions, making sure they work the same, limits how much the program can be altered in strucutre and semantics. by testing end to end the program can be radically reorganised in order to make use of haskell unique features, wihtout falling into the trap of replicating the original python and creating a "imperative like" prgoram in haskell.


to ensure parity the whole way through, an automated script will be developed to systematically perform a differential check on all generated files when a change is made
