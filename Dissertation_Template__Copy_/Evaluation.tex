\chapter{Evaluation}
\label{chap:Evaluation}

This chapter evaluates the finished port against the main aim of the dissertation. It first explains how output comparison was carried out across the seven active repository models, then reports the differences that were found, including the one substantive task manager mismatch and its fix, and finally discusses what the experiment says about behavioural preservation and workflow compatibility.

\section{Experiments}

The evaluation was based on differential comparison between the original Python refiner and the Haskell refiner. For each of the seven active models in the repository, test code was generated once with the Python version and once with the Haskell version. The resulting files were then compared with a diff-based workflow, and each difference was classified as either semantic, where the generated C code changed meaning, or non-semantic, where only formatting changed.

The original plan was to perform this comparison entirely through the existing workflow. In practice, the repository on this Windows machine required additional setup before the experiment could be completed. SPIN was not on the \texttt{PATH}, the checked-in Haskell executable was not usable on Windows, and the current \texttt{testbuilder} configuration still contained Linux-specific absolute paths. To complete the experiment, SPIN was built locally, a temporary cabal wrapper was used to build a Windows Haskell executable, and the saved \texttt{.spn} files were replayed through a small verification client. This extra work matters to the evaluation because it shows that behavioural preservation is stronger than full workflow portability in the current repository state.

The full comparison nevertheless remained faithful to the intended question of the dissertation. The important issue is not whether the Haskell port is faster or more elegant in isolation, but whether it preserves the test generation behaviour of the Python refiner across the existing model set.

This result is slightly more nuanced than simple text equality. Every compared file still differs textually, but after the final fix the remaining differences are all limited to harmless blank lines. For most models the extra line appears immediately before the final SPDX footer. For \texttt{sem-mgr} it appears just before the \texttt{// Task 0} section. These are therefore formatting mismatches rather than behavioural mismatches.

The one substantive difference found during evaluation appeared in \texttt{task-mgr} models 14 and 16. In those files the Python output contained \texttt{do \{ ... \} while (...)} while the Haskell output contained \texttt{do \{\{ ... \}\} while (...)}, which is not valid C. The source of the bug turned out not to be the task manager model itself, but a mismatch between Python \texttt{str.format} semantics and the Haskell template formatter. The refinement dictionary stored literal C braces as doubled braces, and the Haskell formatter replaced placeholders without collapsing \texttt{\{\{} and \texttt{\}\}} back to single braces.

\begin{lstlisting}[language=Haskell, caption={Brace escaping added to the Haskell template formatter}, label={lst:brace-unescape}]
formatTemplate template args =
	let indexed =
				L.foldl'
					(\acc (i, arg) -> T.replace ("{" <> tshow i <> "}") arg acc)
					template
					(zip [0 :: Int ..] args)
			formatted = L.foldl' (\acc arg -> replaceFirst "{}" arg acc) indexed args
	 in T.replace "}}" "}" (T.replace "{{" "{" formatted)
\end{lstlisting}

After rebuilding the Haskell refiner and replaying the saved \texttt{task-mgr} \texttt{.spn} files, the doubled-brace mismatch disappeared. Models 14 and 16 then reduced to the same blank-line-only difference seen elsewhere. This is an important result for the dissertation because it shows that the diff workflow did not merely report mismatches; it also isolated one concrete defect and guided it to a specific fix.

The comparison therefore supports the main claim of the project more strongly than the workflow claim. Behavioural preservation is well supported across the full model set. Workflow compatibility is only partially supported in the current repository state because the Windows experiment still required manual setup and a temporary local build of the Haskell executable.

The incomplete extension experiment remains a limitation of the evaluation. The project can make a strong claim about behavioural preservation, but only a weaker argued claim about maintainability. The implementation suggests that explicit state and clearer decomposition make the Haskell version easier to reason about, but that claim was not tested by a dedicated change task.



\section{Summary}

The evaluation shows that the Haskell refiner preserves the behaviour of the Python version much more strongly than it preserves turnkey workflow compatibility on Windows. One substantive task manager bug was found, traced to template brace escaping, and fixed. After that repair the remaining differences across all seven models were non-semantic blank lines, which means the dissertation can make a strong claim about output preservation while still acknowledging the remaining setup work around the surrounding toolchain.
