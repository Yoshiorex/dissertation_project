\section{Overview of the Solution}

%% Short caption for the table of listings - long caption for the explanation for the reader


The guiding principle of the implementation was a gradual transition from pure python code, to pure haskell code for the principle file refinecommand.py. these files are teh files responsible for turning spin trail files generated into test files. traditionally a replacement would be coded in full and then swapped into the system but to the complex stateful nature of the code being converted, a more gradual appraoch was taken where a hybrid pyhton-haskell phase exists in between the two pure states. 

This was done as a full rewrite could be a risk, spending a large amount of time and work on an implemetation that would have to be redone. Given the large size of the file and the many stateful branches contained within, doing the whole file at once would not be preferable. Hence why an alternative solution was found. by using a bridge to implement a system where the new haskell file could be tested in the pipeline end to end at every point in its development, any large refactoring effort at the end could be avoiding. It would be replaced instead by much smaller testing and debugging of every function.

The testing and debugging were done to lead towards functional equivalence wiht the original python as the python generated tests were confirmed up to the rtems standard for tests.

The key tools used to do the porting would be The bridge script, the diff script and unit testing.

\section{The implementation}

\subsection{The bridge}
a bridge file is created thats able to decide between the python adn teh haskell refine command. it will first try the hasekll adn if the program doesnt respond with expected results, the python version is fallen back on. it is qutie important in that it also handles all communication with the haskell in this phase. communication is handled entirely via the standard input and output. at this point it was important to maintain classes present in the python implementation in order to not break compatibility.

\subsection{The diff script}
crucial to this porting process was constantly checking the generated test files with the ones generated by teh origianl system. at the beginning it was done with a text comparison website but it quickly became apparent that manually copying and pasting 18 separate test files every time a change was made was a waste of time. so a simple script that performed a diff check on the current generated files against a know standard set of test files was created. 

\includecode{Sample of command line output}{it can be seen here that the diff check has found taht compared to the original file, the generated test file has included a superfluous pair of curly brackets}{lst:snippet}{commandline.py}

the file picked up on even the smallest change, including a single additioanl white space line. while not every diff foudn was catastrophic, being able to catch these inconsistencies before tehy cascasded was crucial to teh success of the conversion. By cross checking the changes with the reference dictionaries, the files that stored the actual mappings from spin file messages to c test code, i could isolate where issue came arised and in what scenarios it occured. Fixing these issues were as simple as adding additonal cases in refine command in order to account for the edge case.

unit testing was implemented in refind command.hs early on in order to help figure out why certain changes were occur but they ended up not being particularly helpful. This was because it was easy to test for things like messages coming to and from the bridge, handling basic cases and config file loading, it was very difficult to catch the specific interactions that actually caused spin files to mistranslated.


\subsection{refine command}
this was the main file to be converted. put simply it is the file that takes the output of the model checker and turns it into test code. it does this by taking a line of spin output and matching it via a custom dictionary to a snippet of c code. this custom dictionary stores template c code with gaps where values such as variable names and integers can be substituted in. to do this properly the program also has to keep track of context, for example whether the current output is inside a struct, inside a sequence, or just a standalone value.

in the beginning python code was converted into haskell code line by line aiming to model the original programs behaviour as closely as possible. but what i found developing this way is that even with multiple passes trying to emulate closer and closer to what the python was doing, generated test code would still differ. what made me stop this approach was realizing that converting this way didnt allow for the leveraging of haskells strengths, rendering the exercise practically pointless. so continuing forward python behaviour was more creatively ported to haskell, using the diff script to ensure that the output never strayed, ensuring functional equivalence if not semantic equivalence.

the point where i made this realisation to switch approaches was in the managing of state. the program needs to be aware of whether the current output of the model checker is referring to a struct, a sequence, or just a single value, as the dictionaries have different entries for the same model checker output depending on that context. the python version handles this by making its large match statement even larger with branches and nested match statements for each of these states. each branch is picked based on a number of state variables that were constantly being mutated. this certainly worked and could be emulated in the haskell but was clunky, cumbersome to extend and difficult to reason about.

the new way of approaching this system in a more functional haskelly way was to remove in place state variable mutation and replace it with a state function. this function takes in the previous state, uses it to process one spin line, and then returns a new state, making the state changes explicit. this was the point where the port stopped being a direct copy of the python and started being a haskell program that happened to preserve the same output. what mattered from that point on was not keeping the same internal structure, but keeping the generated test files the same.

this change shows up most clearly in the following snippets.

\paragraph{python state stored and mutated on the object}
\begin{lstlisting}[language=Python, caption={python state stored and mutated on the object}, label={lst:python-state-mutation}]
self.inSTRUCT = False
self.inSEQ = False
self.seqForSEQ = ""
self.inName = ""

case [pid,'SEQ',name]:
    self.inSEQ = True
    self.seqForSEQ = ""
    self.inName = name

case [pid,'SCALAR','_',value]:
    self.seqForSEQ = self.seqForSEQ + " " + value
\end{lstlisting}

in the python version the state lives on the command object. as each spin line is read these values are updated in place, and later branches depend on whatever earlier branches left behind.

\paragraph{haskell state made explicit}
\begin{lstlisting}[language=Haskell, caption={explicit runtime state in the haskell refiner}, label={lst:haskell-runtime-state}]
data RuntimeState = RuntimeState
  { rtInSTRUCT :: Bool
  , rtInSEQ :: Bool
  , rtSeqForSEQ :: Text
  , rtInName :: Text
  , rtDefCode :: [Text]
  , rtDeclCode :: [Text]
  , rtTestCodes :: [(Int, [Text])]
  , rtCurrentId :: Int
  , rtSwitchNo :: Int
  }
\end{lstlisting}

the same information is still present, but it is now grouped into one explicit record. rather than hidden mutation on an object, each function takes a state and returns the next one.

\paragraph{one spin line producing the next state}
\begin{lstlisting}[language=Haskell, caption={processing one SPIN line by returning a new state}, label={lst:haskell-state-pipeline}]
refineSPINLineMain :: [Text] -> RuntimeState -> RuntimeState
refineSPINLineMain ln rt0 =
  let rt1 = collectPIdsTokens ln rt0
      rt2 = if outputSWITCH (rtFlags rt1) then switchIfRequired ln rt1 else rt1
      rt3 = if annoteComments (rtFlags rt2) then logSPINLine ln rt2 else rt2
  in refineSPINLine ln rt3
\end{lstlisting}

this is the clearest expression of the change in approach. instead of one long lived object being updated in place, each stage produces a fresh version of the runtime state before the next stage runs.

\paragraph{sequence handling as an explicit transition}
\begin{lstlisting}[language=Haskell, caption={sequence state handled as an explicit transition}, label={lst:haskell-sequence-state}]
_pidTxt:"SEQ":name:[] ->
  rt { rtInSEQ = True, rtSeqForSEQ = "", rtInName = name }

_pidTxt:"SCALAR":"_":value:[] ->
  rt { rtSeqForSEQ = rtSeqForSEQ rt <> " " <> value }
\end{lstlisting}

sequence handling was where this change felt most useful. in this context a sequence is just an ordered run of values collected between SEQ and END and later emitted through a matching _SEQ template. in the haskell version entering that mode and accumulating those values are both visible directly in the returned state.
