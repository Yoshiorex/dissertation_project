\section{Overview of the Solution}

%% Short caption for the table of listings - long caption for the explanation for the reader


The guiding principle of the implementation was a gradual transition from pure python code, to pure haskell code for the principle file refinecommand.py. these files are teh files responsible for turning spin trail files generated into test files. traditionally a replacement would be coded in full and then swapped into the system but to the complex stateful nature of the code being converted, a more gradual appraoch was taken where a hybrid pyhton-haskell phase exists in between the two pure states. 

This was done as a full rewrite could be a risk, spending a large amount of time and work on an implemetation that would have to be redone. Given the large size of the file and the many stateful branches contained within, doing the whole file at once would not be preferable. Hence why an alternative solution was found. by using a bridge to implement a system where the new haskell file could be tested in the pipeline end to end at every point in its development, any large refactoring effort at the end could be avoiding. It would be replaced instead by much smaller testing and debugging of every function.

The testing and debugging were done to lead towards functional equivalence wiht the original python as the python generated tests were confirmed up to the rtems standard for tests.

The key tools used to do the porting would be The bridge script, the diff script and unit testing.

\subsection{The bridge}
a bridge file is created thats able to decide between the python adn teh haskell refine command. it will first try the hasekll adn if the program doesnt respond with expected results, the python version is fallen back on. it is qutie important in that it also handles all communication with the haskell in this phase. communication is handled entirely via the standard input and output. at this point it was important to maintain classes present in the python implementation in order to not break compatibility.

\subsection{The diff script}
crucial to this porting process was constantly checking the generated test files with the ones generated by teh origianl system. at the beginning it was done with a text comparison website but it quickly became apparent that manually copying and pasting 18 separate test files every time a change was made was a waste of time. so a simple script that performed a diff check on the current generated files against a know standard set of test files was created.

the file picked up on even the smallest change, including a single additioanl white space line. while not every diff foudn was catastrophic, being able to catch these inconsistencies before tehy cascasded was crucial to teh success of the conversion. By cross checking the changes with the reference dictionaries, the files that stored the actual mappings from spin file messages to c test code, i could isolate where issue came arised and in what scenarios it occured. Fixing these issues were as simple as adding additonal cases in refine command in order to account for the edge case.

unit testing was implemented in refind command.hs early on in order to help figure out why certain changes were occur but they ended up not being particularly helpful. This was because it was easy to test for things like messages coming to and from the bridge, handling basic cases and config file loading, it was very difficult to catch the specific interactions that actually caused spin files to mistranslated.


\subsection{refine command}
this was the main file to be converted, put simply it is the file that turns the files generated from the model checker and turns them into  test code. it does this by taking a line of spin output and matching it via a custom dictionary to a snippet of c cod e. this custom dictionary has entries for all spin lines and template c code with interchangeable parts where sepcific values like variable names and integer values can be subbed in. the program does this  while keeping track of things like whether or not the program in currently translating a struct or an array.

in the beginning python code was converted into haskell code line by line aiming to model the original programs behaviour as closely as possible. but what i found developing this way, is that even with multiple passes trying to emulate closer and closer to what the python was doing, generated test code would differ. what made me stop this appraoch is realizing that converting this way didnt allow for the leveraging of haskells strengths, rendering teh exercise practically pointless. so continuing forward python behaviour was more creatively ported to haskell, using the diff script to ensure that the output never strayed, ensuring fucntinoal equivalence if not semantic equivalence. 
the point where i made this realisation to switch approaches was in the managing of state. The program needs to be aware of if the current ouput of the model checker is referring to a struct or an array or just a single value as the dictionaries have different entries for the same model cehcker output depending on these details about the state. the python version handles this by making its large match statement even larger with branches and nested match statements for each of these states. each branch is picked based on a number of state variables that were constantly being mutated. this certainly worked and could be emulated in the haskell but was clunky, cumbersome to extend and difficult to reason about. 

the new way of approaching this system in a more functional haskelly way was to remove in place state variable mutation and replace it with a state function. this function takes in the previous state, uses it to precoess one spin line, and then returns a new state, making the state changes explicit 



In the end the programs ended up differing in some key ways


**1) How a SPIN line is handled**

Before (stringly‑typed, big `case` on raw tokens):
```haskell
refineSPINLine :: [Text] -> RuntimeState -> RuntimeState
refineSPINLine spinLine rt =
  case spinLine of
    pidTxt:"CALL":name:args -> ...
    pidTxt:"WAIT":value:[] -> ...
    -- many more cases
```

After (parse once → typed opcode):
```haskell
parseSpinLine :: [Text] -> SpinOp
parseSpinLine tokens = ... -- OpCall, OpWait, OpInit, etc.

refineSpinOp :: SpinOp -> Refine ()
refineSpinOp op =
  case op of
    OpCall pid name args -> ...
    OpWait pid value -> ...
```

**2) State management**

Before (manual threading):
```haskell
refineSPINLineMain ln rt0 =
  let rt1 = collectPIdsTokens ln rt0
      rt2 = if outputSWITCH (rtFlags rt1) then switchIfRequired ln rt1 else rt1
      rt3 = if annoteComments (rtFlags rt2) then logSPINLine ln rt2 else rt2
  in refineSPINLine ln rt3
```

After (single pipeline in a state monad):
```haskell
refineSPINLineMain ln rt0 =
  execRefine (refineLine ln) rt0
  where
    refineLine tokens = do
      collectPIdsTokens tokens
      flags <- getsR rtFlags
      when (outputSWITCH flags) (switchIfRequired tokens)
      when (annoteComments flags) (logSPINLine tokens)
      refineSpinOp (parseSpinLine tokens)
```

**3) Safety of list access**

Before: `head`, `!!` used in a few spots.  
After: replaced with pattern matching in `parseSpinLine` and rendering.

**4) Output accumulation**

Before: appending to lists (costly).  
After: prepending + reversing once at render time.
